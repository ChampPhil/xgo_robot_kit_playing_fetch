Build a tower from **purple, orange and light-blue blocks**, in a user-entered
**bottom-to-top** order. Blocks should be selectable from different positions in view,
not assigned fixed starting slots. Their known height is **25 mm**; width, depth, weight,

The intended cycle is:

1. Observe all three boxes and select the next requested color.
2. Align to its taught pickup view and perform the pickup.
3. Check that the box is held. If a confirmed miss or drop leaves that color on the floor,
   retry the same color within a bounded attempt limit.
4. Carry it to a fixed stack target, align, and place it at the appropriate layer.
5. Verify placement before committing that layer and proceeding to the next color.

and physical placement have **not** been confirmed.

### Retry and verification behavior

- Default: **three total pickup attempts per color**, including the first attempt; configurable 1–5.
- Positive visual grip: exactly one requested-color candidate in a calibrated held region,
  and none in the disjoint floor region, across fresh observations.
- Confirmed miss/drop: requested color on floor and no held candidate. This can trigger
  a separately taught recovery motion and another attempt.
- Neither region, both regions, duplicates, stale/blurred frames or contradictory evidence:
  stop. Disappearance alone does not count as success.
- Optional empty/occupied gripper raw-byte bands can corroborate vision, but no measured
  bands have been supplied. Raw position is not a force/contact sensor.
- Placement requires marker corner agreement, an empty held region, and correctly ordered,
  adjacent, horizontally aligned colored faces in a taught inspection region.
- This is **2-D visual evidence**, not proof of mechanical stability or a calibrated 3-D tower.

### Motion and resource behavior

- No motor initialization in observation, reference capture, configuration checking or simulation.
- Live execution validates every asset before XGO construction. Startup construction itself
  resets/stands the robot; execution must be explicitly supervised.
- The Mac sends heartbeats at 20 Hz over SSH. Missing heartbeat/EOF, a >0.5 s control-loop
  stall, stale camera, invalid/low battery, phase deadlines or a 600 s session limit stop work.
- Live runtime owns camera 0 and `/dev/ttyAMA0`; do not run another serial reader alongside it.
- Carry/check/return/recovery routes preserve the current claw command. Placement has one
  explicit claw-open event and cannot walk/turn. Route validation requires a recorded leg stop.
- Cancellation stops legs without resetting, opening the claw or automatically standing.
- Routes are taught for a **bounded workcell**, not general navigation or obstacle avoidance.
- Layer support-surface heights are nominally **0, 25 and 50 mm**. Each needs a separately
  taught motion; adding 25 mm directly to arm z is not validated when body posture changes.
- Unknown/null arm starts are rejected; saturated servo bytes do not establish actual pose.

## Teaching support already added

Teleop now accepts `--record-motion-only` and forwards `--teach-dir` from the Mac sender.
X can record a route without a visible box, saving commands and one starting reference image
without a continuous video dataset. An explicit commanded arm pose is required first.
Release walking keys before stopping X so the file contains its leg-stop event.

The route recorder **does not capture an endpoint reference image/state**. References for
carry-check/inspection views still need a separate camera-only capture at the taught pose.
The existing `--capture-reference` command can consume the teleop MJPEG stream and a pose file
or recording reference, avoiding a second camera owner.
